# AI 个人学习系统：工作包 8 多 Agent 协作与共享状态顶层设计分析

日期：2026-09-30  
定位：工作包 8 的设计准备，明确需要解决的决定、继承边界、设计拆分与检验办法；不是正式协作方案或软件实现规格。

**工作包 8 要解决的是：同一学习目标经过不同执行者、会话和版本之后，谁能作什么决定，依据是否仍然有效，接收方能否继续真正尚未完成的工作。**应先从具体决定推出责任和授权，再考虑怎样分配给 Agent。不能先列一组 Agent 名单，再把前面工作包分装进去。

下文以【继承】表示前包已有约定，以【设计建议】表示本轮建议下一版落实的组织方式，以【待定】表示需要方案取舍或真实试用的信息。示例均为假设，不能写入用户真实学习记录。

【继承】以下规则已经成立，不应重新投票选择：

1. 工作包 2 维护目标与判据，3 维护证据解释和诊断，4 维护内容与材料用途，5 维护教学活动，6 维护策略使用，计划责任方维护预算内安排。8 落实责任如何持续有效，不能收走所有专业判断权。
2. 高层必须提供关键任务、参考锚点、学习者应承担的操作、重要分支与授权；仅给“让用户理解”不足以交付。执行者有局部调整权，普通措辞、合格等价替换、允许帮助和授权内评分不需逐轮审批。
3. 高理论上限与本次范围分开。复杂证明、方法构造和综合判断应有可靠参考与审查能力；预算不足可以分段或缩范围，不能让执行模型的便利决定目标降标。
4. 原答、实际帮助、目标与任务版本、事件时间和相关学习／反馈时间可回查。高层先看原答、条件和判据，再看总结；换 Agent、隐藏答案、重做评分均不重置暴露，也不增加独立证据。
5. 当前能力的“支持、未达、未知、混合”与判断的“可使用、待复核、已撤销”不是一回事。材料可用、活动完成、目标通过也不能合成一个状态。
6. 个人记录删除后，按剩余支持保留、收窄或撤销判断，并更新摘要与相关安排。不能以追溯为由拒绝删除，也不能从遗留副本恢复或保留影子作答。

## 二、前包尚未解决的协作问题

目前可承接的主要缺口是运行约定尚未细化，并非需要推翻前包。下面的张力应在方案中作具体取舍。

| 需要协调的两方面 | 下一版必须回答的问题 |
|---|---|
| 关键判断集中负责，实时互动需要自由 | 哪些普通决定可以直接生效？哪种变化会触及目标、证据用途、内容或承诺范围，从而超出当前授权？ |
| 高能力模型承担关键设计，等待和费用需受控 | 高层何时必须亲自参与？能否提前交付足够具体的参考和分支，使执行者合理继续？高层缺席时哪些用途必须暂停？ |
| 并行工作提高准备效率，决定不能互相覆盖 | 两个执行者基于不同版本提交结果时，谁检查兼容性？谁决定采用、部分采用或退回？什么变化立即限制旧安排？ |
| 摘要便于恢复，复杂判断需要原始依据 | 常规恢复最少读什么？出现评分争议、重要跳过或诊断冲突时必须回看什么？原记录缺失时如何限制结论？ |
| 原始事件应保真，用户有纠正与删除权 | 如何区分对原始事件的勘误、对解释的修订和删除？导出怎样带上必要条件又避免复制全部聊天？ |
| 交接需要闭环，不能变成重复审批 | 哪些结果只是收到，哪些已经承担责任，哪些已成为有效安排？无回应、拒收和迟到回执由谁继续处理？ |

旧架构对删除后判断处理的简述，应按 2／3 和 C0 后续方案的细化执行：剩余证据充分可保留，部分充分则收窄，失去依据则撤销。不能机械解释为“删一条就清零”。工作包 7 尚在设计，8 也不能把本轮对 7 的建议写成既有计划政策。

## 三、建议拆成六项设计责任

这些是设计问题，不规定六个 Agent 或六个模块。相容责任可以合并，由同一执行者兼任时仍需辨认决定性质与依据。

### 1. 决定与授权

【设计建议】先列“实际要改变什么”，再填写提出者、可直接决定者、最终责任方、复核条件和用户决定边界。至少覆盖目标／判据、重要能力结论／重大诊断、材料用途、关键教学设计、局部帮助与常规评分、策略更换、计划承诺和记录控制。

升级理由应落在错误后果、依据不确定性、变化范围、反馈时效及授权资源上，不能只写“复杂则升级”。例如，更换措辞可以直接做；变式改变成立条件须重新核验相应用途；删去证明要求涉及目标变化；缩短本次证明覆盖涉及计划范围。这几件事需要不同路径。

必须设计高层交付是否足够的检查：执行者应能据此出题、反馈、辨别关键分支与停止；不足时返回具体缺项，不凭空补出关键参考。相容的责任合并，不等于靠同一生成答案自证正确；多模型同意、共享来源的多次复述也不是独立核验。

### 2. 共享信息的语义与读取

【设计建议】复用现有记录，给每类必要信息说明维护责任、用途、更新触发和有效性限制，不发明统一“学习状态”。至少辨认：当前目标与判据、学科参考及材料用途、原始表现与条件、条件化判断、暂定诊断、当前活动及帮助、计划承诺与未完成项、父任务与恢复点、待处理交接。

优先引用原记录，避免每个 Agent 各存一份全量画像。轻量摘要应能定位原答和条件，不能成为新的事实来源。用于恢复的简表与用于重要复核的证据范围可以不同。内容已经准备、已经采用、实际展示以及用户实际使用分别记录；没有显示日志不能证明未暴露，打开材料也不等于已经读完。

### 3. 委派、交接与接管

【设计建议】一份最小委派应说明需要解决的决定、所据版本、可读依据、授权范围、预期产物、资源边界、停止条件及返回对象。新增委派必须有独立价值，不能因仍然不确定就无限转交；转交不会扩大原授权，受托者不能靠再次委派取得自己没有的权限。

交接结果至少能区分待接收、已接收待处理和已经形成的处理结果。处理结果可能是安排、部分采用、延期、合并、拒绝或不再投入，含义由相应责任方确认。发送成功和一句“知道了”均不等于完成；无回应不把责任转移给学习者。

接管者需确认当前有效依据、可继续范围、受限用途、未决项和停止／返回条件。可以在同一份短记录中完成，不要求额外签批文档。交接基于旧版本时先查兼容性，再判断是否仍需执行；不得让迟到回执复活已撤回任务。突然中断且没有结束摘要时，从已确认事件恢复，不能猜补最后作答、帮助或决定。

### 4. 版本、冲突与纠错传播

【设计建议】明确什么是建议、什么已获专业决定、什么已进入当前安排。并行产生的不同原始作答可以分别保存；相互矛盾的判断不能自动合并，旧版本结果不能用最后写入覆盖或多数投票处理。

依据被撤销或材料失效时，应立即停用受影响用途，不等完整新版方案写完。内容纠错分别追踪“来源—材料／任务／答案—评分与判断—安排”以及“来源—目标／判据—任务与评价—安排”。各责任方回报自己的处理结果，8 保证依赖没有漏接，不代做所有复核。

必须分别确认内容已更正、实际误导已修复、旧评分和判断已重审。原答足够时直接重评并撤回误判引起的补课，不让用户重新考试来修复系统错误。依赖关系不全时标出影响范围未知，不能当作没有影响。

### 5. 用户控制与记录维护

【设计建议】明确用户怎样查看当前依据、质疑评分、纠正个人信息、导出和删除记录，以及哪些派生摘要、判断和安排随之复核。事实勘误可据依据更正，评分异议可以保留；不能把确有提示的表现改记为无提示。导出至少应使接收者辨认原始表现、帮助条件、当前判断和限制；具体格式待实现阶段选择。

保存以未来判断和恢复需要为限，不默认永久保留完整聊天，也不为推断独立性而隐蔽监测。删除后非个人学科参考可继续保留；不能借保留参考之名保存已删除的个人作答或无依据的个人暴露结论。方案应写清语义上的删除范围和使用限制，不承诺尚未选定的存储、备份或权限技术已经具备能力。

### 6. 协作成本与简化

【设计建议】把高层准备、等待、重复核验、交接遗漏、上下文重建、费用及用户打断纳入成本。出现同一问题反复委派、重复索取原答、普通互动总要等待或多角色只复述彼此时，应能减少交接或合并相容责任。

具体 Agent 数量、模型与技术选型留待后续。方案需提出比较办法：保持目标、材料和判据相近，比较分层协作与同一执行者兼任的较简单安排，分别看内容正确性、教学执行、学习结果与协作成本。纸上走查只能查出设计漏洞，不能证明多 Agent 更有效。

## 四、与工作包 7 共用的接口

【设计建议】本轮两包可以并行，但需共同采用以下责任划分，并在正式方案阶段复核。

| 环节 | 主要责任 | 交接必须保留什么 |
|---|---|---|
| 后续学习需求 | 5 提出目标内未完成工作；6 补替代、使用条件和成本 | 目标版本、未支持工作、必要条件与建议时窗的区别、原答帮助及时间引用、材料和父任务限制；退卡不自动新增欠账 |
| 计划承诺 | 7 在预算内选择安排、缩范围、延后、合并或不再投入 | 唯一有效计划／当前展开单、决定理由、受影响范围、下一可执行位置及真实处理结果 |
| 承诺生效与交接 | 8 落实授权责任、采用版本、接收与接管 | 谁作决定、基于什么、何时可执行、谁尚未处理；拒收、迟到或冲突结果的去向 |
| 中断恢复 | 7 决定恢复什么及本次重新承诺多少；8 保证可信上下文与授权连续 | 当前有效目标、判断、材料用途、原答与帮助／时间背景、停止原因、父任务返回点和受限用途 |

日历合并不代表不同证据条件已满足；7 须由教学方确认线索、资源、间隔及关键工作的兼容性。8 保存这些约束的归属与版本，不另设调度算法。经过一段时间、换会话或换 Agent，都不能自动改写能力判断。

## 五、下一版应交付什么，怎样验收

下一版应形成一套可试用的责任与协作规范：授权矩阵、共享信息说明、完整交接与接管示例、版本／冲突规则、纠错与用户控制流程、跨会话恢复规则，以及简化和验证办法。每项写清输入、关键判断、行动、责任、停止与恢复，而不止罗列问题。

至少用以下假设情境检查，逐一展示“依据—谁决定—交出什么—接收结果—当前有效状态—下一步”。

| 情境 | 必须能查到的结果 |
|---|---|
| 普通活动顺利完成，高层预先给足设计 | 执行者在授权内完成反馈、评分和收束，无重复冷启动或例行全员签批 |
| 复杂证明缩时，局部完成后换 Agent | 父任务和中间产物保留；目标标准不变，局部成功不冒充整体通过；恢复承诺由 7 决定 |
| 两个执行者依据不同版本提出相反建议，旧回执迟到 | 原始证据不覆盖；专业责任方判断兼容性，旧建议不能覆盖当前有效决定 |
| 参考有错，多个模型都认可错误答案 | 按学科依据核验，两条纠错链均检查；原答可重评，错误补课撤回，同意票数不作正确性证据 |
| 意外展示答案后换执行者，高层暂不可用 | 暴露历史连续；相关独立结论受限；不依赖争议且已授权的活动可继续 |
| 删除一份关键证据后旧执行者迟到回传 | 分别走查剩余支持充分、部分和不足时的保留／收窄／撤销；摘要与安排同步，旧缓存和迟到结果不复活已删除内容 |
| 突然中断，没有结束摘要；用户质疑帮助记录 | 从已确认事件恢复，缺失项未知；核对事实勘误并保存异议，不伪造无提示证据 |
| 接收方未回应或拒收，委派反复绕回 | 待处理责任、继续范围与收束路径可辨；不虚报已经安排，也不无限委派 |

【待定】责任矩阵、接管规则与保留／导出／删除语义由本包定；真实课程、预算、核验资源及授权粒度在实例化时校准；模型、存储、通信与具体数据格式留到实现阶段。它们与前包已定的专业归属分别列明，不能把已定边界重新悬置，也不因真实输入未齐而停止概念设计。

工作包 8 的设计通过标志，是换人后仍可据正确版本继续，关键判断有责任、权限和可回查依据，失败有受限继续与恢复路径。真实教学收益与多 Agent 的净收益，留给有限试用及工作包 9—10 的贯通验证。
